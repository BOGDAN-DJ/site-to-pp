# LaLune/CSQTT на Cudy TR3000 (OpenWrt, arm64, 256 МБ flash / 512 МБ RAM)

Этот каталог — не форк проекта [LaLune](https://github.com/Endlad2/LaLune), а
патч-набор для его каталога `OpenWRT/`: переписанный демон, который
**на самом деле поднимает туннель** на роутере, плюс инструкция по установке
под конкретно ваш Cudy TR3000.

## Зачем переписывать демон

Я склонировал `Endlad2/LaLune` и `Endlad2/csqtt-core` и прочитал код. Штатный
`OpenWRT/main.go` в LaLune:

1. Запускал `csqtt-client` с флагом `--tun <имя>`, которого в текущем CLI
   ядра просто нет (есть только `--tun-uds`, а он работает исключительно на
   Android через передачу файлового дескриптора по Unix-сокету) — ядро
   валилось с ошибкой парсинга аргументов при старте.
2. Даже если бы флаг существовал: демон создавал kernel TUN-интерфейс
   (`ip tuntap add ...`) и сразу переключал на него `default route`, но
   **ничего не перекачивало пакеты** между этим TUN и ядром. На Desktop-версии
   (Windows/Wintun, отчасти Linux) этим занимается отдельный кусок Go-кода
   (`Desktop/*/Libs/bridge.go` + платформенный `Start(udpConn, ...)`), а для
   OpenWRT такой код никогда не был написан — в `go.mod` даже осталась
   неиспользуемая зависимость `github.com/songgao/water` (Go-библиотека для
   TUN/TAP), явно оставленная "на будущее".
3. Не прокладывал обходные маршруты к самому VPN-серверу — включив
   default route через ещё не поднятый туннель, роутер потерял бы связь с
   сервером, через который этот туннель поднимается.
4. Не трогал firewall — даже с рабочим туннелем клиенты в LAN не получили бы
   выход в интернет (нет masquerade/forwarding на новый интерфейс).

Код в этом каталоге чинит все четыре пункта. Демон
(`GOOS=linux GOARCH=arm64 CGO_ENABLED=0`) собирается чисто, статически
слинкован, весит ~6.6 МБ (Go 1.27) и проверен на живом роутере — см.
раздел «Проверено на железе».

## Компоненты и совместимость с Cudy TR3000

Cudy TR3000 — MediaTek MT7981 (Filogic 820), 2×Cortex-A53, **arm64**,
таргет OpenWrt `mediatek/filogic`. 256 МБ — это встроенная flash-память
(eMMC/NAND), а не оперативная — ОЗУ на этой модели 512 МБ, так что запас по
памяти для демона (~6 МБ) и клиента (~15–25 МБ) вполне комфортный. Компилировать
что-либо прямо на роутере не нужно — обе части кросс-компилируются на
обычном ПК/CI и просто копируются как готовые бинарники.

Современный OpenWrt (24.10 и новее, в том числе то, что вы называете
"OpenWrt 25") по умолчанию использует **firewall4 (nftables)** — код здесь
рассчитан именно на него (использует `list device` в зоне firewall,
специфичную для fw4 фичу).

## glibc vs musl: в чём проблема и как она решена

`csqtt-core` собирает готовые релизы клиента под
`aarch64-unknown-linux-gnu` — это **glibc**, а стоковый OpenWrt использует
**musl**. Проверено на релизе `2026.09.07.15.04`:

```
$ file client-linux-arm64
ELF 64-bit LSB pie executable, ARM aarch64, dynamically linked,
interpreter /lib/ld-linux-aarch64.so.1, for GNU/Linux 3.7.0
```

Нужны `libc.so.6`, `libm.so.6`, `libgcc_s.so.1` и символы вплоть до
**`GLIBC_2.38`**. На роутере есть только `/lib/ld-musl-aarch64.so.1`,
поэтому ядро не находит ELF-интерпретатор:

```
# ./client --help
ash: ./client: not found     # rc=127, при том что файл на месте и +x
```

Обманчивое сообщение: «not found» относится не к самому файлу, а к его
интерпретатору.

**Entware, который раньше предлагался тут как обходной путь, не подходит** —
нужной версии glibc (2.38, это середина 2023 года) там нет ни в одном
варианте.

Рабочее решение из коробки — `install-glibc-shim.sh`. Он кладёт в
`/opt/glibc` загрузчик и libc из пакетов Debian trixie arm64 (~3 МБ),
а `/usr/bin/csqtt-client` делает обёрткой:

```sh
#!/bin/sh
exec /opt/glibc/ld-linux-aarch64.so.1 \
	--library-path /opt/glibc \
	/opt/csqtt/csqtt-client-glibc "$@"
```

Системные `/lib` и `/usr/lib` при этом не трогаются вообще, так что на
musl-окружение роутера это никак не влияет. Удаляется полностью:
`rm -rf /opt/glibc /opt/csqtt`. Проверено на железе — ядро запускается и
поднимает туннель.

Это всё же прослойка, а не правильное решение. Правильное —
пересобрать `csqtt-core` под `aarch64-unknown-linux-musl`
(`rustup target add aarch64-unknown-linux-musl`, либо `cargo zigbuild`).
Мешает то, что в `Cargo.toml` есть `aws-lc-rs` (собирает C-код AWS-LC) и
вендоренный `primp` — обе зависимости тянут нативный код и под musl
кросс-собираются негладко. Самый дешёвый путь — попросить автора
`csqtt-core` добавить musl-таргет в свой CI: в `.github/workflows/build.yml`
это правка на несколько строк рядом с уже имеющейся сборкой под arm64.

## Проверено на железе

Всё, что описано ниже, прогнано на реальном роутере:

| | |
|---|---|
| Железо | Cudy TR3000 (MT7981, 2×Cortex-A53, 512 МБ RAM) |
| OpenWrt | 25.12.5, r33051-f5dae5ece4, kernel 6.12.94 |
| Таргет | `mediatek/filogic`, `aarch64_cortex-a53` |
| Firewall | fw4 (nftables) |
| Пакетный менеджер | `apk` (а не `opkg` — в 25.x его уже нет) |

Результат: туннель поднимается, трафик из LAN ходит через него.

```
[TUN] TUNCONF получен: IP=10.66.67.3 DNS=77.88.8.8,77.88.8.1
[ROUTE] Обходной маршрут для relay/TURN 95.163.34.160
[TUN] Трафик обнаружен (Активных > 0)
[TUN] Туннель поднят: csqtt0 10.66.67.3/32, default route -> csqtt0
[CORE] [СТАТИСТИКА] Активных: 18 | Трафик: 4.52 МБ
```

Заодно подтвердились два предположения, которые до этого никто не
проверял: firewall4 действительно принимает «живой» TUN-интерфейс через
`list device` (в nftables появляется `oifname "csqtt0" jump srcnat_csqtt`),
и обходные маршруты для relay-адресов, вычитанных из лога ядра на лету,
прокладываются корректно.

## Установка

### Вариант «одной командой»

С машины, которая находится в одной сети с роутером:

```sh
./install.sh root@192.168.1.1 ./csqtt-daemon-arm64
./install-glibc-shim.sh root@192.168.1.1        # ядро + glibc-прослойка
```

`install.sh` проверит архитектуру и наличие `fw4`, при необходимости
доставит `kmod-tun`, скопирует файлы, включит сервис и покажет статус; уже
существующий `/etc/csqtt/csqtt.conf` он не перезатирает. Третьим аргументом
можно передать готовое ядро, если оно у вас уже собрано под musl — тогда
`install-glibc-shim.sh` не нужен.

### Чего не хватает в стоковом образе

Это грабли, на которые я наступил при первой установке — скрипты их теперь
обходят сами, но знать полезно:

- **`kmod-tun` не установлен.** `/dev/net/tun` отсутствует, `modprobe tun`
  возвращает 255, и `Connect()` падает на `setupTunDevice`. Ставится через
  `apk add kmod-tun`; пакет кладёт `/etc/modules.d/30-tun`, так что после
  перезагрузки модуль поднимается сам.
- **`scp` не работает.** В OpenWrt нет `/usr/libexec/sftp-server`, а `scp`
  начиная с OpenSSH 9.0 по умолчанию ходит по SFTP и падает с
  `Connection closed`. Нужен `scp -O` (legacy-протокол).
- **`curl` не установлен** — есть только `uclient-fetch`, притворяющийся
  `wget`.
- **Нельзя копировать поверх работающего демона** — `ETXTBSY`
  («Text file busy»). Сначала `/etc/init.d/csqtt stop`.

### Про CRLF

Если клонировать репозиторий на Windows с `core.autocrlf=true` (значение по
умолчанию), checkout выдаёт файлы с CRLF, и на роутере ломается shebang:
`#!/bin/sh /etc/rc.common\r` заставляет ash искать файл `/etc/rc.common\r`,
а `/etc/init.d/csqtt` падает с `can't open '/etc/rc.common'`. Лечится
файлом `.gitattributes` в этом каталоге — в самом репозитории всегда лежал
LF, проблема была чисто на стороне checkout.

Дальше — вручную, по шагам:

### 1. Соберите демон (или возьмите готовый бинарник)

```sh
cd OpenWRT
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-s -w" -o csqtt-daemon-arm64 .
```

### 2. Скопируйте на роутер

```sh
scp csqtt-daemon-arm64 root@192.168.1.1:/usr/sbin/csqtt-daemon
scp files/csqtt.init      root@192.168.1.1:/etc/init.d/csqtt
scp files/csqtt.conf.example root@192.168.1.1:/etc/csqtt/csqtt.conf
scp /path/to/csqtt-client-arm64  root@192.168.1.1:/usr/bin/csqtt-client   # см. раздел про glibc/musl выше
```

### 3. На роутере

```sh
chmod +x /usr/sbin/csqtt-daemon /usr/bin/csqtt-client /etc/init.d/csqtt
vi /etc/csqtt/csqtt.conf   # заполнить PEER, PASSWORD, VK — см. ниже
/etc/init.d/csqtt enable
/etc/init.d/csqtt start
```

### 4. Проверка

```sh
curl -s http://127.0.0.1:8080/api/status
curl -s http://127.0.0.1:8080/api/logs | tail -n 40
curl -s -X POST http://127.0.0.1:8080/api/connect
```

Если через 5–10 секунд в логах видно `[TUN] Туннель поднят: csqtt0 ...` —
значит TUNCONF получен, трафик пошёл, default route и firewall настроены.

Дальше — с любого устройства в LAN `curl ifconfig.me` должен вернуть IP
сервера, а не ваш реальный. **Но этот тест врёт, если сервер CSQTT стоит за
тем же интернет-каналом, что и роутер** (например, на машине в вашей же
домашней сети): выходной адрес тогда одинаковый и с туннелем, и без него,
так что проверка пройдёт в любом случае. В такой конфигурации смотрите на
счётчики интерфейса — они не обманут:

```sh
ip -s link show csqtt0     # RX/TX должны расти
```

Отключение: `curl -s -X POST http://127.0.0.1:8080/api/disconnect`.

### Страховка на первый запуск

Демон переключает default route и правит firewall, так что при первом
прогоне полезно подстелить соломки — завести «мёртвую руку», которая сама
всё откатит, если вы потеряете управление:

```sh
cat > /tmp/csqtt-deadman.sh <<'EOF'
#!/bin/sh
sleep 600
[ -f /tmp/csqtt-deadman ] || exit 0
curl -s -X POST http://127.0.0.1:8080/api/disconnect >/dev/null 2>&1
/etc/init.d/csqtt stop
EOF
chmod +x /tmp/csqtt-deadman.sh
touch /tmp/csqtt-deadman
start-stop-daemon -S -b -x /tmp/csqtt-deadman.sh
```

Убедились, что всё работает — `rm /tmp/csqtt-deadman`, и откат не сработает.
Запускать именно через `start-stop-daemon -b`: `nohup ... &` в ash не
переживает закрытие SSH-сессии, проверено.

## Автозапуск, кнопка и несколько WAN

### Как маршрут по умолчанию устроен сейчас

Демон **не удаляет** маршрут WAN. Свой маршрут через туннель он добавляет
с метрикой 1, а у WAN-интерфейсов метрики больше, так что ядро выбирает
туннель само:

```
default dev csqtt0 scope link metric 1
default via 192.168.31.100 dev eth0 proto static src 192.168.31.179 metric 300
```

Отсюда три полезных следствия: отключение — это удаление одной строки без
восстановления чужого маршрута; переключение между WAN остаётся заботой
netifd; а если демон умрёт, не прибравшись, роутер останется с рабочим
интернетом, а не без маршрута вообще.

### AUTOCONNECT

```sh
AUTOCONNECT='1'    # в /etc/csqtt/csqtt.conf
```

Демон поднимет туннель при старте, дождавшись появления default route
(до 2 минут — на S95 DHCP на WAN может быть ещё не отработан). Если
интернет так и не появился, автоподключение просто отменяется.

Включать стоит после того, как туннель проверен вручную. Даже неудачное
автоподключение теперь не оставит роутер без интернета, но пока
`AUTOCONNECT='0'`, перезагрузка — самый простой способ вернуть всё как было.

### Кнопка

Обработчик ставится в `/etc/rc.button/BTN_0` — это кнопка **`mode`**
(в devicetree `gpio-keys/mode`, `linux,code = 0x100 = BTN_0`). Короткое
нажатие переключает туннель через `POST /api/toggle`; результат виден по
индикатору и в `logread -e csqtt-button`:

| Мигания | Что произошло |
|---|---|
| 2 | туннель включён |
| 1 | туннель выключен |
| 5 | ошибка, подробности в `logread` |

Кнопка `reset` намеренно не занимается: она нужна для failsafe, и
переопределять её — значит лишиться способа вернуть роутер к жизни.

Решение о том, включать или выключать, принимает сам демон в `/api/toggle`
под общим мьютексом. Если бы скрипт кнопки сначала спрашивал `/api/status`,
а потом дёргал `connect` либо `disconnect`, между двумя запросами состояние
могло бы смениться — например, от двойного нажатия или от watchdog.

### Несколько WAN (USB-модем + Ethernet)

Типичная конфигурация Cudy TR3000 — модем как основной канал, Ethernet как
резервный:

```
network.usbwan.device='usb0'  metric='10'
network.wan.device='eth0'     metric='300'
```

Меньшая метрика выигрывает, поэтому при воткнутом модеме нижележащим
каналом становится `usb0`. Само по себе переключение делает netifd, но
обходные маршруты к peer и TURN-серверам прибиты к конкретному шлюзу — и
после смены канала указывали бы в никуда. Туннель при этом умирал бы молча:
интерфейс `csqtt0` никуда не девается, просто перестаёт передавать данные.

Поэтому демон раз в 3 секунды перечитывает нижележащий default route
(`watchUnderlay`) и при смене шлюза или интерфейса перекладывает все свои
обходные маршруты на новый канал:

```
[ROUTE] Канал сменился: via 192.168.31.100 dev eth0 -> via 10.x.x.1 dev usb0,
        перекладываю обходные маршруты
```

Собственный маршрут туннеля при этом не трогается — метрика 1 выигрывает у
любого WAN.

## Откуда взять PEER/PASSWORD/VK

Из вашей ссылки вида:

```
csqtt://connect?v=2&host=HOST&peer=PORT&password=PASSWORD&hashes=HASH1+HASH2+HASH3
```

- `PEER` в конфиге = `HOST:PORT` (склеить `host` и `peer` из ссылки через
  двоеточие).
- `PASSWORD` = `password` из ссылки как есть.
- `VK` = `hashes` из ссылки, `+` замените на запятые (или оставьте пробелы —
  демон сам нормализует любые разделители).

## Ограничения этой реализации

- **Один конфиг**, без мультипрофильного UI из `Frontend/app.html` (тот
  ожидает полноценный REST — `/api/configs`, `/api/settings` — которого нет
  ни в оригинальном демоне LaLune, ни здесь). Настройка — через
  `/etc/csqtt/csqtt.conf` или `POST /api/config/update`.
- Только IPv4 (как и весь остальной проект на данный момент).
- Автоподключение при загрузке выключено по умолчанию (`AUTOCONNECT='0'`),
  чтобы перезагрузка гарантированно возвращала роутер в состояние без
  туннеля. Включается одной строкой в конфиге — см. раздел ниже.
- **DNS туннеля толком не применяется.** Демон дописывает выданные серверы
  в `/etc/resolv.conf`, но на OpenWrt это симлинк на `/tmp/resolv.conf`,
  где первой строкой стоит `nameserver 127.0.0.1` — то есть локальный
  dnsmasq. Он и отвечает всем клиентам в LAN, а свои апстримы берёт из
  `/tmp/resolv.conf.auto`, куда демон не пишет. В результате дописанные
  адреса влияют только на резолвинг самого роутера, да и то как запасные.
  Плюс `/tmp` теряется при перезагрузке. Сломать это не может (запросы
  всё равно уходят в туннель вместе со всем остальным трафиком), но если
  нужен именно DNS туннеля для LAN — правильное место `uci set
  dhcp.@dnsmasq[0].server=...`, а не `/etc/resolv.conf`.
- Обходные маршруты строятся по IP из `PEER`/`TURN_HOST` и по IP, которые
  ядро упоминает в логах со словом `TURN`/`Relay` во время работы — если
  сервер меняет relay на лету, соответствующий маршрут добавится
  автоматически, но с небольшой задержкой (до ~0.4 c, интервал опроса лога).
  Для адресов, доступных напрямую (peer в той же подсети, что и WAN
  роутера), обходной маршрут намеренно не прокладывается: их уже
  обслуживает connected-маршрут, который длиннее default и переживёт его
  подмену, а заворот такого адреса «via шлюз» на части upstream-роутеров
  просто не работает.
- При первом подключении в лог попадает
  `[UCI] uci delete firewall.csqtt.device -> exit status 1` — это шум, а не
  ошибка: удаляется опция, которой ещё нет.
- **После отключения в nftables остаются семь пустых цепочек**
  (`input_csqtt`, `output_csqtt`, `forward_csqtt`, `accept_to_csqtt`,
  `reject_from_csqtt`, `reject_to_csqtt`, `srcnat_csqtt`). Из uci-конфига
  зона удаляется полностью, маршруты и TUN снимаются, но `fw4 reload`
  оставляет сами цепочки. Они пустые и на них никто не ссылается, так что
  ни на фильтрацию, ни на NAT это не влияет; при следующем подключении они
  переиспользуются. Убрать можно вручную — `fw4 restart`. Специально
  переключать `firewallDown()` на `restart` не стал: перестраивать весь
  firewall при каждом отключении — цена выше, чем польза от косметики.
- `restoreDefaultRoute` возвращает маршрут без атрибутов `proto static` и
  `src` (было `default via 192.168.31.100 dev eth0 proto static
  src 192.168.31.179 metric 300`, стало то же самое без двух последних).
  На выбор исходящего адреса это не влияет, пока на интерфейсе один IP.
