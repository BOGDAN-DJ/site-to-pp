# LaLune/CSQTT на Cudy TR3000 (OpenWrt, arm64, 256 МБ flash / 512 МБ RAM)

Этот каталог — не форк проекта [LaLune](https://github.com/Endlad2/LaLune), а
патч-набор для его каталога `OpenWRT/`: переписанный демон, который
**на самом деле поднимает туннель** на роутере, плюс инструкция по установке
под конкретно ваш Cudy TR3000.

## Зачем переписывать демон

Я склонировал `Endlad2/LaLune` и `Endlad2/csqtt-core` и прочитал код. Штатный
`OpenWRT/main.go` в LaLune:

1. Запускал `csqtt-client` с флагом `--tun <имя>`, которого в текущем CLI
   ядра просто нет (есть только `--tun-uds`, а он работает исключительно на
   Android через передачу файлового дескриптора по Unix-сокету) — ядро
   валилось с ошибкой парсинга аргументов при старте.
2. Даже если бы флаг существовал: демон создавал kernel TUN-интерфейс
   (`ip tuntap add ...`) и сразу переключал на него `default route`, но
   **ничего не перекачивало пакеты** между этим TUN и ядром. На Desktop-версии
   (Windows/Wintun, отчасти Linux) этим занимается отдельный кусок Go-кода
   (`Desktop/*/Libs/bridge.go` + платформенный `Start(udpConn, ...)`), а для
   OpenWRT такой код никогда не был написан — в `go.mod` даже осталась
   неиспользуемая зависимость `github.com/songgao/water` (Go-библиотека для
   TUN/TAP), явно оставленная "на будущее".
3. Не прокладывал обходные маршруты к самому VPN-серверу — включив
   default route через ещё не поднятый туннель, роутер потерял бы связь с
   сервером, через который этот туннель поднимается.
4. Не трогал firewall — даже с рабочим туннелем клиенты в LAN не получили бы
   выход в интернет (нет masquerade/forwarding на новый интерфейс).

Код в этом каталоге чинит все четыре пункта. Демон
(`GOOS=linux GOARCH=arm64 CGO_ENABLED=0`) собирается чисто, статически
слинкован, весит ~6.6 МБ (Go 1.27) и проверен на живом роутере — см.
раздел «Проверено на железе».

## Компоненты и совместимость с Cudy TR3000

Cudy TR3000 — MediaTek MT7981 (Filogic 820), 2×Cortex-A53, **arm64**,
таргет OpenWrt `mediatek/filogic`. 256 МБ — это встроенная flash-память
(eMMC/NAND), а не оперативная — ОЗУ на этой модели 512 МБ, так что запас по
памяти для демона (~6 МБ) и клиента (~15–25 МБ) вполне комфортный. Компилировать
что-либо прямо на роутере не нужно — обе части кросс-компилируются на
обычном ПК/CI и просто копируются как готовые бинарники.

Современный OpenWrt (24.10 и новее, в том числе то, что вы называете
"OpenWrt 25") по умолчанию использует **firewall4 (nftables)** — код здесь
рассчитан именно на него (использует `list device` в зоне firewall,
специфичную для fw4 фичу).

## glibc vs musl: в чём проблема и как она решена

`csqtt-core` собирает готовые релизы клиента под
`aarch64-unknown-linux-gnu` — это **glibc**, а стоковый OpenWrt использует
**musl**. Проверено на релизе `2026.09.07.15.04`:

```
$ file client-linux-arm64
ELF 64-bit LSB pie executable, ARM aarch64, dynamically linked,
interpreter /lib/ld-linux-aarch64.so.1, for GNU/Linux 3.7.0
```

Нужны `libc.so.6`, `libm.so.6`, `libgcc_s.so.1` и символы вплоть до
**`GLIBC_2.38`**. На роутере есть только `/lib/ld-musl-aarch64.so.1`,
поэтому ядро не находит ELF-интерпретатор:

```
# ./client --help
ash: ./client: not found     # rc=127, при том что файл на месте и +x
```

Обманчивое сообщение: «not found» относится не к самому файлу, а к его
интерпретатору.

**Entware, который раньше предлагался тут как обходной путь, не подходит** —
нужной версии glibc (2.38, это середина 2023 года) там нет ни в одном
варианте.

Рабочее решение из коробки — `install-glibc-shim.sh`. Он кладёт в
`/opt/glibc` загрузчик и libc из пакетов Debian trixie arm64 (~3 МБ),
а `/usr/bin/csqtt-client` делает обёрткой:

```sh
#!/bin/sh
exec /opt/glibc/ld-linux-aarch64.so.1 \
	--library-path /opt/glibc \
	/opt/csqtt/csqtt-client-glibc "$@"
```

Системные `/lib` и `/usr/lib` при этом не трогаются вообще, так что на
musl-окружение роутера это никак не влияет. Удаляется полностью:
`rm -rf /opt/glibc /opt/csqtt`. Проверено на железе — ядро запускается и
поднимает туннель.

Это всё же прослойка, а не правильное решение. Правильное —
пересобрать `csqtt-core` под `aarch64-unknown-linux-musl`
(`rustup target add aarch64-unknown-linux-musl`, либо `cargo zigbuild`).
Мешает то, что в `Cargo.toml` есть `aws-lc-rs` (собирает C-код AWS-LC) и
вендоренный `primp` — обе зависимости тянут нативный код и под musl
кросс-собираются негладко. Самый дешёвый путь — попросить автора
`csqtt-core` добавить musl-таргет в свой CI: в `.github/workflows/build.yml`
это правка на несколько строк рядом с уже имеющейся сборкой под arm64.

## Проверено на железе

Всё, что описано ниже, прогнано на реальном роутере:

| | |
|---|---|
| Железо | Cudy TR3000 (MT7981, 2×Cortex-A53, 512 МБ RAM) |
| OpenWrt | 25.12.5, r33051-f5dae5ece4, kernel 6.12.94 |
| Таргет | `mediatek/filogic`, `aarch64_cortex-a53` |
| Firewall | fw4 (nftables) |
| Пакетный менеджер | `apk` (а не `opkg` — в 25.x его уже нет) |

Результат: туннель поднимается, трафик из LAN ходит через него.

```
[TUN] TUNCONF получен: IP=10.66.67.3 DNS=77.88.8.8,77.88.8.1
[ROUTE] Обходной маршрут для relay/TURN 95.163.34.160
[TUN] Трафик обнаружен (Активных > 0)
[TUN] Туннель поднят: csqtt0 10.66.67.3/32, default route -> csqtt0
[CORE] [СТАТИСТИКА] Активных: 18 | Трафик: 4.52 МБ
```

Заодно подтвердились два предположения, которые до этого никто не
проверял: firewall4 действительно принимает «живой» TUN-интерфейс через
`list device` (в nftables появляется `oifname "csqtt0" jump srcnat_csqtt`),
и обходные маршруты для relay-адресов, вычитанных из лога ядра на лету,
прокладываются корректно.

## Установка

### Вариант «одной командой»

С машины, которая находится в одной сети с роутером:

```sh
./install.sh root@192.168.1.1 ./csqtt-daemon-arm64
./install-glibc-shim.sh root@192.168.1.1        # ядро + glibc-прослойка
```

`install.sh` проверит архитектуру и наличие `fw4`, при необходимости
доставит `kmod-tun`, скопирует файлы, включит сервис и покажет статус; уже
существующий `/etc/csqtt/csqtt.conf` он не перезатирает. Третьим аргументом
можно передать готовое ядро, если оно у вас уже собрано под musl — тогда
`install-glibc-shim.sh` не нужен.

### Чего не хватает в стоковом образе

Это грабли, на которые я наступил при первой установке — скрипты их теперь
обходят сами, но знать полезно:

- **`kmod-tun` не установлен.** `/dev/net/tun` отсутствует, `modprobe tun`
  возвращает 255, и `Connect()` падает на `setupTunDevice`. Ставится через
  `apk add kmod-tun`; пакет кладёт `/etc/modules.d/30-tun`, так что после
  перезагрузки модуль поднимается сам.
- **`scp` не работает.** В OpenWrt нет `/usr/libexec/sftp-server`, а `scp`
  начиная с OpenSSH 9.0 по умолчанию ходит по SFTP и падает с
  `Connection closed`. Нужен `scp -O` (legacy-протокол).
- **`curl` не установлен** — есть только `uclient-fetch`, притворяющийся
  `wget`.
- **Нельзя копировать поверх работающего демона** — `ETXTBSY`
  («Text file busy»). Сначала `/etc/init.d/csqtt stop`.

### Про CRLF

Если клонировать репозиторий на Windows с `core.autocrlf=true` (значение по
умолчанию), checkout выдаёт файлы с CRLF, и на роутере ломается shebang:
`#!/bin/sh /etc/rc.common\r` заставляет ash искать файл `/etc/rc.common\r`,
а `/etc/init.d/csqtt` падает с `can't open '/etc/rc.common'`. Лечится
файлом `.gitattributes` в этом каталоге — в самом репозитории всегда лежал
LF, проблема была чисто на стороне checkout.

Дальше — вручную, по шагам:

### 1. Соберите демон (или возьмите готовый бинарник)

```sh
cd OpenWRT
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-s -w" -o csqtt-daemon-arm64 .
```

### 2. Скопируйте на роутер

```sh
scp csqtt-daemon-arm64 root@192.168.1.1:/usr/sbin/csqtt-daemon
scp files/csqtt.init      root@192.168.1.1:/etc/init.d/csqtt
scp files/csqtt.conf.example root@192.168.1.1:/etc/csqtt/csqtt.conf
scp /path/to/csqtt-client-arm64  root@192.168.1.1:/usr/bin/csqtt-client   # см. раздел про glibc/musl выше
```

### 3. На роутере

```sh
chmod +x /usr/sbin/csqtt-daemon /usr/bin/csqtt-client /etc/init.d/csqtt
vi /etc/csqtt/csqtt.conf   # заполнить PEER, PASSWORD, VK — см. ниже
/etc/init.d/csqtt enable
/etc/init.d/csqtt start
```

### 4. Проверка

```sh
curl -s http://127.0.0.1:8080/api/status
curl -s http://127.0.0.1:8080/api/logs | tail -n 40
curl -s -X POST http://127.0.0.1:8080/api/connect
```

Если через 5–10 секунд в логах видно `[TUN] Туннель поднят: csqtt0 ...` —
значит TUNCONF получен, трафик пошёл, default route и firewall настроены.

Дальше — с любого устройства в LAN `curl ifconfig.me` должен вернуть IP
сервера, а не ваш реальный. **Но этот тест врёт, если сервер CSQTT стоит за
тем же интернет-каналом, что и роутер** (например, на машине в вашей же
домашней сети): выходной адрес тогда одинаковый и с туннелем, и без него,
так что проверка пройдёт в любом случае. В такой конфигурации смотрите на
счётчики интерфейса — они не обманут:

```sh
ip -s link show csqtt0     # RX/TX должны расти
```

Отключение: `curl -s -X POST http://127.0.0.1:8080/api/disconnect`.

### Страховка на первый запуск

Демон переключает default route и правит firewall, так что при первом
прогоне полезно подстелить соломки — завести «мёртвую руку», которая сама
всё откатит, если вы потеряете управление:

```sh
cat > /tmp/csqtt-deadman.sh <<'EOF'
#!/bin/sh
sleep 600
[ -f /tmp/csqtt-deadman ] || exit 0
curl -s -X POST http://127.0.0.1:8080/api/disconnect >/dev/null 2>&1
/etc/init.d/csqtt stop
EOF
chmod +x /tmp/csqtt-deadman.sh
touch /tmp/csqtt-deadman
start-stop-daemon -S -b -x /tmp/csqtt-deadman.sh
```

Убедились, что всё работает — `rm /tmp/csqtt-deadman`, и откат не сработает.
Запускать именно через `start-stop-daemon -b`: `nohup ... &` в ash не
переживает закрытие SSH-сессии, проверено.

## Автозапуск, кнопка и несколько WAN

### Как устроена маршрутизация

Основная таблица маршрутизации **не трогается вообще**. Туннельный default
живёт в отдельной таблице 100, а попадает в неё только трафик из LAN — по
двум правилам `ip rule`:

```
0:      from all lookup local
29000:  from 192.168.1.0/24 lookup main suppress_prefixlength 0
29001:  from 192.168.1.0/24 lookup 100
32766:  from all lookup main
```

Правило 29000 разрешает по основной таблице всё, у чего есть конкретный
маршрут (соседи по локальной сети, WAN-подсеть), но `suppress_prefixlength 0`
пропускает мимо default route. Всё остальное доходит до 29001 и уходит в
туннель. Без первого правила трафик между машинами внутри локальной сети
тоже заворачивался бы в туннель.

Проверить, что получилось, можно прямо на роутере:

```sh
ip route get 8.8.8.8                                   # роутер: via ... dev eth0
ip route get 8.8.8.8 from 192.168.1.100 iif br-lan     # клиент: dev csqtt0 table 100
```

#### Почему не проще — через default с метрикой 1

Так и было сделано сначала, и это оказалось неверно. В основную таблицу
попадал заодно трафик самого ядра `csqtt-client`, а ядру, чтобы поднять
или восстановить сессии, надо ходить на серверы авторизации VK. Эти
запросы уходили в туннель, который ядро в этот момент и пытается починить.

Замкнутый круг: стоило туннелю упасть — и подняться сам он уже не мог
никогда. Наблюдалось вживую после того, как выдернули USB-модем:

```
[CORE] ... dns error: Yandex DNS не ответил за 5 секунд для login.vk.ru
[CORE] [СТАТИСТИКА] Активных: 0
```

Ядро осталось в памяти и бесконечно крутило попытки авторизации, а
watchdog умел замечать только смерть процесса. Туннель пришлось поднимать
вручную переключателем.

**Плата за такое решение:** собственный трафик роутера (обновления пакетов,
его own запросы) идёт мимо туннеля. Для VPN-шлюза это нормально и даже
желательно — управление и восстановление связи не зависят от туннеля.
Если нужно иначе, вариант есть: запускать ядро под отдельным uid и
добавить `ip rule uidrange` на него, тогда через туннель пойдёт всё, кроме
служебного трафика ядра.

### Переключатель

На Cudy TR3000 туннелем управляет переключатель **`mode`** (в devicetree
`gpio-keys/mode`, `linux,code = 0x100`, то есть `BTN_0`). Обработчик
ставится в `/etc/rc.button/BTN_0`.

Это именно переключатель с двумя устойчивыми положениями, а не кнопка,
поэтому положение прямо задаёт состояние:

| Положение | GPIO | Действие | Мигания |
|---|---|---|---|
| `pressed` | линия low (активна) | включить туннель | 2 |
| `released` | линия hi | выключить туннель | 1 |
| | | ошибка | 5 |

Подробности — в `logread -e csqtt-button`.

### Индикация

Состояние туннеля показывается штатным светодиодом:

| Индикатор | Состояние туннеля |
|---|---|
| белый мигает | подключается |
| белый ровно | поднят, трафик идёт |
| красный ровно | выключен, роутер ходит напрямую |

На Cudy TR3000 `white:status` и `red:power` — два входа одного физического
двухцветного светодиода. «Туннеля нет» показывается красным, а не
погашенным индикатором: тёмный светодиод выглядел бы так, будто роутер
выключен, хотя он работает и просто ходит в интернет напрямую.

Настраивается в конфиге (`LED`, `LED_IDLE`); пустое значение отключает
индикацию. Исходное состояние обоих светодиодов демон запоминает при старте
и возвращает при выходе — сняли демон, и роутер выглядит как раньше.

Миганием управляет ядро через триггер `timer`, а не горутина демона: так
индикация не зависит от того, чем занят процесс, и переживает даже его
зависание.

Светодиодом владеет **только демон**. Скрипт переключателя его не трогает
намеренно: скрипту известен лишь факт нажатия, и если бы индикацией
управлял он, она показывала бы намерение вместо результата — при неудачном
подключении светодиод врал бы.

Toggle для тумблера был бы неверен: procd вызывает обработчик при переводе
в каждое из положений своим `ACTION`, так что «переключить» на одном
направлении не вызывалось бы вовсе, а на другом срабатывало бы вслепую — и
положение переключателя перестало бы соответствовать состоянию. Прямое
отображение ещё и идемпотентно: повторный вызов с тем же `ACTION` ничего не
ломает. Переменную `SEEN` обработчик не смотрит — для тумблера это время с
прошлой смены положения, оно может быть любым.

Эндпоинт `POST /api/toggle` в демоне остаётся — он полезен для настоящей
кнопки без фиксации. Решение о направлении там принимается под тем же
мьютексом, что и само действие: если бы скрипт сначала спрашивал
`/api/status`, а потом дёргал `connect` либо `disconnect`, между двумя
запросами состояние могло бы смениться.

Переключатель `reset` намеренно не занимается: он нужен для failsafe, и
переопределять его — значит лишиться способа вернуть роутер к жизни.

### AUTOCONNECT

```sh
AUTOCONNECT='switch'    # в /etc/csqtt/csqtt.conf
SWITCH_LABEL='mode'
```

| Значение | Поведение при старте демона |
|---|---|
| `0` (по умолчанию) | ничего не делать, ждать команды |
| `1` | всегда подключаться |
| `switch` | подключаться, только если переключатель в положении «включено» |

Режим `switch` нужен из-за того, что `/etc/rc.button/BTN_0` вызывается
только при **смене** положения. После перезагрузки смены не было, и демон
сам по себе не знает, куда выставлен тумблер: при `AUTOCONNECT='1'` он
поднял бы туннель, даже если переключатель стоит в положении «выключено».
Поэтому на старте положение читается напрямую из
`/sys/kernel/debug/gpio` — уровень линии сопоставляется с полярностью
(`ACTIVE LOW` → активному состоянию соответствует `lo`). Формат debugfs не
является стабильным ABI, так что если разобрать не удалось, демон честно
пишет об этом в лог и не подключается, а не гадает.

В любом режиме демон ждёт появления default route до 2 минут: procd
запускает его на S95, а DHCP на WAN к этому моменту может быть ещё не
отработан. Если интернет так и не появился, автоподключение отменяется.

Включать автозапуск стоит после того, как туннель проверен вручную. Даже
неудачное автоподключение не оставит роутер без интернета — маршрут WAN
не удаляется, — но пока `AUTOCONNECT='0'`, перезагрузка остаётся самым
простым способом вернуть всё как было.

### Несколько WAN (USB-модем + Ethernet)

Типичная конфигурация Cudy TR3000 — модем как основной канал, Ethernet как
резервный:

```
network.usbwan.device='usb0'  metric='10'
network.wan.device='eth0'     metric='300'
```

Меньшая метрика выигрывает, поэтому при воткнутом модеме роутер уходит в
интернет через `usb0`.

**Демону здесь делать нечего.** Основная таблица маршрутизации принадлежит
netifd, а туннельная таблица 100 содержит только `default dev csqtt0` и от
канала не зависит. Так что переключение между WAN целиком отрабатывает
netifd, и никакого слежения за сменой канала в демоне нет.

Проверено на железе, все три перехода:

| Действие | Результат |
|---|---|
| Воткнули модем при живом Ethernet | `usb0` стал основным каналом, туннель не дрогнул |
| Выдернули Ethernet | ничего не изменилось, канал уже был `usb0` |
| Вернули Ethernet, вынули модем | вернулись на `eth0` |

Туннель переживает смену канала **без переподключения**: PID ядра не
менялся, 18 сессий остались на месте, переустановки TURN не потребовалось —
сокеты ядра не привязаны к конкретному исходящему адресу, поэтому оно
просто начинает пользоваться новым маршрутом.

Косвенное, но убедительное подтверждение того, что путь действительно
меняется: задержка до 8.8.8.8 выросла с 73 до 108 мс при переходе на
модем, а внешний IP остался прежним. Так и должно быть — выходной адрес
определяет сервер CSQTT, а не канал роутера.

### Если туннель всё же завис

Watchdog следит за двумя вещами: не умер ли процесс ядра и давно ли ядро
сообщало о живых сессиях. Если `Активных: 0` держится дольше 90 секунд,
туннель считается зависшим и переподключается:

```
[WATCHDOG] нет активных сессий уже 1m30s, переподключаюсь...
```

Второе условие добавлено после того, как туннель на живом роутере молча
умер и не поднялся: ядро осталось в памяти и бесконечно крутило попытки
авторизации, а смерть процесса — единственное, что watchdog умел замечать
раньше. Первопричину (трафик ядра уходил в собственный туннель) устранила
policy-маршрутизация, но зависнуть туннель может и по другим причинам —
сервер перезапустили, связь моргнула.

## Сервисы провайдера, резолвящиеся в приватный адрес

Отдельный случай, на который легко потратить вечер, поставив неверный
диагноз. Разобран на реальном примере: АТС провайдера `ats.karelia.pro`,
доступная из домашней сети, но не с роутера.

### Симптом и ложный след

Домен «не резолвится с роутера», SIP-клиент отдаёт `DNS Timeout 503`.
Напрашивается вывод: запись видна только внутри сети провайдера, а
глобальный DNS про неё не знает.

Вывод неверный. Проверка занимает минуту:

```sh
for srv in 192.168.31.100 1.1.1.1 8.8.8.8; do nslookup ats.karelia.pro $srv; done
```

Домен резолвится **везде**, включая публичные резолверы, и всюду отдаёт
один и тот же адрес — `10.0.43.139`. Зона обслуживается обычным публичным
DNS-хостингом. Проблема не в том, где живёт запись, а в том, **на что она
указывает**: адрес приватный (RFC1918).

### Настоящая причина

У dnsmasq в OpenWrt по умолчанию включена защита от DNS rebinding
(`rebind_protection='1'`): ответы от внешних резолверов, содержащие
приватные адреса, отбрасываются. Это разумная защита — она мешает внешнему
сайту заставить браузер обратиться внутрь вашей сети, — но здесь срабатывает
на легитимный сервис.

В логе это видно прямым текстом:

```
dnsmasq[1]: possible DNS-rebind attack detected: ats.karelia.pro
```

Поэтому смотреть надо `logread`, а не гадать по симптому: запросы к
апстримам проходят, режется ответ уже на роутере.

### Решение

Исключить конкретный домен из проверки, не отключая её целиком:

```sh
uci add_list dhcp.@dnsmasq[0].rebind_domain='karelia.pro'
uci commit dhcp
/etc/init.d/dnsmasq restart
```

Исключение распространяется и на поддомены. Настройка живёт в
`/etc/config/dhcp`, то есть переживает перезагрузку и попадает в штатный
`sysupgrade -b`.

Отключать `rebind_protection` целиком не стоит: она защищает всю локальную
сеть, а проблема касается одного домена.

### Маршрутизация: обход туннеля был бы ошибкой

Второй, менее очевидный слой. Напрашивается мысль завернуть сеть провайдера
мимо туннеля — телефонии полезнее короткий путь, да и SIP через VPN обычно
приносит лишний NAT и джиттер:

```sh
ip rule add to 10.0.0.0/8 lookup main priority 28000   # НЕ ДЕЛАЙТЕ ТАК
```

На этом роутере такое правило **ломает доступ к АТС**, и проверка это
показала. Когда WAN — USB-модем, приватная сеть провайдера с мобильного
канала недостижима в принципе, а туннель выходит на машину, которая внутри
этой сети находится. То есть туннель оказывается **единственным** путём:

| Откуда | Результат |
|---|---|
| С роутера (ходит мимо туннеля, через модем) | 100% потерь |
| Из LAN через туннель | работает, 104 мс, джиттер 5 мс |

При домашнем Ethernet в WAN работают оба пути, просто через туннель он
длиннее необходимого. Усложнять код ради этого не стоит: конфигурация
рабочая в обоих случаях.

Что стоит помнить: **при выключенном туннеле и воткнутом модеме такие
сервисы недоступны**. Это не поломка, а свойство сети — с мобильного
канала в приватную сеть домашнего провайдера хода нет.

### Логи, переживающие перезагрузку

И системный лог OpenWrt (`logread`), и кольцевой буфер демона (`/api/logs`)
живут в оперативной памяти. Роутер перезагрузился или у него сняли питание —
и от инцидента не осталось ничего. На живом железе это случилось дважды
подряд: туннель не поднимался, питание выдернули, разбираться стало не по
чему.

Поэтому демон дописывает хвост своего буфера в `/etc/csqtt/incidents.log`
при трёх событиях:

- неудачная попытка подключения (перед назначением повтора);
- срабатывание watchdog (ядро умерло или туннель завис);
- завершение по сигналу.

Каждая запись начинается заголовком с временем и причиной:

```
===== 2026-09-08 09:54:49 | не удалось подключиться: таймаут подключения =====
```

При обычном отключении по команде файл не пишется — это не инцидент.

Смотреть можно из панели (вкладка «Инциденты» рядом с журналом), через
API или напрямую:

```sh
ssh root@192.168.1.1 'cat /etc/csqtt/incidents.log'
curl -s http://192.168.1.1:8080/api/logs/incidents
```

Файл ограничен 96 КБ, при переполнении обрезается спереди по границе строки:
свежий инцидент всегда важнее давнего. Пишется редко и по несколько
килобайт, так что износ флеша несущественный. Права `0600`, как у конфига;
пароль в лог не попадает — аргументы запуска ядра маскируются
(`safeArgsForLog`), — но в записях видны адреса серверов и детали сети.

В `/etc/sysupgrade.conf` файл намеренно не добавлен: это диагностика, а не
настройка, и тащить её через обновление прошивки незачем.

## Веб-панель

Демон отдаёт небольшую панель по адресу роутера в локальной сети:

```
http://192.168.1.1:8080/
```

Показывает состояние туннеля (поднят / подключается / выключен), число
живых потоков из общего числа воркеров, трафик, время в сети, текущий
канал в интернет, IP туннеля и адрес сервера. Там же кнопка включения и
последние 60 строк журнала. Обновляется раз в 3 секунды.

Вторая половина панели — поле для ссылки `csqtt://connect?...`. Вставленная
ссылка разбирается на сервере (`POST /api/config/link`) и **накладывается**
на существующий конфиг: из неё берутся только адрес сервера, пароль и
VK-хеши, а `N`, `OBFS`, `AUTOCONNECT` и прочие настройки остаются как были.
Если ссылка не разобралась, конфиг не трогается вовсе.

Пароль панель не показывает никогда — ни до, ни после сохранения; в лог
попадает только адрес сервера и количество хешей.

Панель самодостаточна: ни одного внешнего ресурса, потому что роутер
вполне может оказаться без интернета ровно в тот момент, когда панель
нужнее всего.

### На каких адресах слушает

Демон поднимает два слушателя на общем обработчике:

| Адрес | Зачем |
|---|---|
| `127.0.0.1:8080` | всегда; через него ходят скрипт переключателя и `install.sh` |
| LAN-адрес роутера | панель из локальной сети; берётся из uci автоматически |

Слушать `:8080` на всех интерфейсах было бы неправильно: панель принимает и
показывает параметры подключения, а от WAN её отделял бы только firewall —
слишком тонкая защита для таких данных. Адрес переопределяется через
`LISTEN` в конфиге; если LAN-адрес определить не удалось, демон честно
пишет об этом в лог и остаётся на одном loopback (панель тогда доступна
через `ssh -L 8080:127.0.0.1:8080 root@роутер`).

**Аутентификации у панели нет.** Кто имеет доступ в вашу локальную сеть,
тот может включить и выключить туннель и заменить ссылку подключения.
Для домашней сети это обычно приемлемо, но знать об этом стоит.

## Бэкап и восстановление

```sh
./backup.sh root@192.168.1.1 ~/router-backups
```

Кладёт в каталог с меткой времени четыре файла:

| Файл | Что это |
|---|---|
| `overlay.tar.gz` | полный слепок `/overlay/upper` — пакеты, бинарники, конфиги, ключи |
| `config.tar.gz` | штатный `sysupgrade -b`, только список из `/etc/sysupgrade.conf` |
| `packages.txt` | установленные пакеты, на случай ручной пересборки |
| `info.txt` | версия прошивки, разделы, сеть, состояние туннеля на момент снятия |
| `RESTORE.txt` | инструкция с готовой ссылкой на образ ровно вашей версии |

Восстановление:

```sh
./restore.sh root@192.168.1.1 ~/router-backups/2026.../overlay.tar.gz
```

Скрипт сверяет версию прошивки с записанной в `info.txt`, спрашивает
подтверждение, останавливает сервисы, распаковывает слепок и перезагружает
роутер.

### Почему штатного `sysupgrade -b` недостаточно

Он сохраняет только то, что перечислено в `/etc/sysupgrade.conf`, плюс
базовый набор — на этом роутере изначально 35 файлов, среди которых **не
было ни одного нашего**: ни демона, ни `/etc/csqtt/` с ключами подключения,
ни обработчика переключателя, ни `/opt` с ядром и glibc-прослойкой. То есть
следующее же обновление прошивки стёрло бы всю установку.

Поэтому `install.sh` дописывает в `/etc/sysupgrade.conf` конфиг и обработчик
переключателя — то, что восстановить неоткуда. Бинарники туда намеренно не
добавляются: они крупные, а `sysupgrade` держит список в оперативной памяти
во время прошивки; их проще поставить заново тем же `install.sh`.

Полноценный бэкап — это `overlay.tar.gz`: всё, что отличается от заводского
образа, одним архивом (~15 МБ сжатых из 27 МБ).

### Версия прошивки должна совпадать

Если роутер прошит начисто, ставьте **ровно ту же** версию OpenWrt, из
которой снят бэкап: пакеты `kmod-*` жёстко привязаны к версии ядра и от
другой версии просто не загрузятся. `restore.sh` это проверяет и
отказывается работать при несовпадении (обходится через `FORCE=1`, если
понимаете риск). Прямая ссылка на нужный образ лежит в `RESTORE.txt`.

### Проверяйте бэкап распаковкой

Бэкап, который не разворачивали, — это ещё не бэкап. Безопасная проверка,
без применения к системе:

```sh
scp -O overlay.tar.gz root@192.168.1.1:/tmp/
ssh root@192.168.1.1 'mkdir -p /tmp/v && tar -xzf /tmp/overlay.tar.gz -C /tmp/v &&
  md5sum /tmp/v/usr/sbin/csqtt-daemon /usr/sbin/csqtt-daemon'
```

Суммы должны совпасть. Для этого бэкапа так и проверено — сошлись все шесть
ключевых файлов, и ядро из архива запускается.

### В архивах лежат секреты

`overlay.tar.gz` и `config.tar.gz` содержат пароль VPN
(`/etc/csqtt/csqtt.conf`), пароли Wi-Fi (`/etc/config/wireless`), приватные
host-ключи SSH и `authorized_keys`. Каталог `backups/` и `*.tar.gz` внесены
в `.gitignore`, но хранить архивы всё равно надо соответственно — не в
общих папках и не в облаке без шифрования.

## Откуда взять PEER/PASSWORD/VK

Из вашей ссылки вида:

```
csqtt://connect?v=2&host=HOST&peer=PORT&password=PASSWORD&hashes=HASH1+HASH2+HASH3
```

- `PEER` в конфиге = `HOST:PORT` (склеить `host` и `peer` из ссылки через
  двоеточие).
- `PASSWORD` = `password` из ссылки как есть.
- `VK` = `hashes` из ссылки, `+` замените на запятые (или оставьте пробелы —
  демон сам нормализует любые разделители).

## Ограничения этой реализации

- **Один конфиг**, без мультипрофильного UI из `Frontend/app.html` (тот
  ожидает полноценный REST — `/api/configs`, `/api/settings` — которого нет
  ни в оригинальном демоне LaLune, ни здесь). Настройка — через
  `/etc/csqtt/csqtt.conf` или `POST /api/config/update`.
- Только IPv4 (как и весь остальной проект на данный момент).
- Автоподключение при загрузке выключено по умолчанию (`AUTOCONNECT='0'`),
  чтобы перезагрузка гарантированно возвращала роутер в состояние без
  туннеля. Включается одной строкой в конфиге — см. раздел ниже.
- **DNS туннеля толком не применяется.** Демон дописывает выданные серверы
  в `/etc/resolv.conf`, но на OpenWrt это симлинк на `/tmp/resolv.conf`,
  где первой строкой стоит `nameserver 127.0.0.1` — то есть локальный
  dnsmasq. Он и отвечает всем клиентам в LAN, а свои апстримы берёт из
  `/tmp/resolv.conf.auto`, куда демон не пишет. В результате дописанные
  адреса влияют только на резолвинг самого роутера, да и то как запасные.
  Плюс `/tmp` теряется при перезагрузке. Сломать это не может (запросы
  всё равно уходят в туннель вместе со всем остальным трафиком), но если
  нужен именно DNS туннеля для LAN — правильное место `uci set
  dhcp.@dnsmasq[0].server=...`, а не `/etc/resolv.conf`.
- **Собственный трафик роутера идёт мимо туннеля** — в туннель
  заворачивается только то, что пришло из LAN. Это осознанный размен: так
  ядро может достучаться до серверов авторизации VK, чтобы туннель поднять
  или восстановить. Подробности и альтернатива через `uidrange` — в разделе
  о маршрутизации.
- Заворачиваются подсети LAN-интерфейса (`network.lan.device` из uci). Если
  нужны другие — перечислите их в `LAN_SUBNETS` через запятую. Гостевые
  сети и прочие интерфейсы автоматически не подхватываются.
- При первом подключении в лог попадает
  `[UCI] uci delete firewall.csqtt.device -> exit status 1` — это шум, а не
  ошибка: удаляется опция, которой ещё нет.
- Строки, которые ядро повторяет постоянно (`[СТАТИСТИКА]` раз в секунду,
  keepalive `ChannelBind` и `Refresh` на каждую из 18 сессий), попадают в
  лог не чаще раза в минуту. Иначе кольцевой буфер демона на 1000 строк
  забивался ими целиком примерно за четверть часа, а поскольку stdout
  демона procd отправляет в системный лог, `logread` на 97% состоял из
  csqtt и вытеснял всё остальное. Актуальная статистика при этом всегда
  доступна целиком в `/api/status`, поле `core_stats`.
- **После отключения в nftables остаются семь пустых цепочек**
  (`input_csqtt`, `output_csqtt`, `forward_csqtt`, `accept_to_csqtt`,
  `reject_from_csqtt`, `reject_to_csqtt`, `srcnat_csqtt`). Из uci-конфига
  зона удаляется полностью, маршруты и TUN снимаются, но `fw4 reload`
  оставляет сами цепочки. Они пустые и на них никто не ссылается, так что
  ни на фильтрацию, ни на NAT это не влияет; при следующем подключении они
  переиспользуются. Убрать можно вручную — `fw4 restart`. Специально
  переключать `firewallDown()` на `restart` не стал: перестраивать весь
  firewall при каждом отключении — цена выше, чем польза от косметики.
- `restoreDefaultRoute` возвращает маршрут без атрибутов `proto static` и
  `src` (было `default via 192.168.31.100 dev eth0 proto static
  src 192.168.31.179 metric 300`, стало то же самое без двух последних).
  На выбор исходящего адреса это не влияет, пока на интерфейсе один IP.
