# LaLune/CSQTT на Cudy TR3000 (OpenWrt, arm64, 256 МБ flash / 512 МБ RAM)

Этот каталог — не форк проекта [LaLune](https://github.com/Endlad2/LaLune), а
патч-набор для его каталога `OpenWRT/`: переписанный демон, который
**на самом деле поднимает туннель** на роутере, плюс инструкция по установке
под конкретно ваш Cudy TR3000.

## Зачем переписывать демон

Я склонировал `Endlad2/LaLune` и `Endlad2/csqtt-core` и прочитал код. Штатный
`OpenWRT/main.go` в LaLune:

1. Запускал `csqtt-client` с флагом `--tun <имя>`, которого в текущем CLI
   ядра просто нет (есть только `--tun-uds`, а он работает исключительно на
   Android через передачу файлового дескриптора по Unix-сокету) — ядро
   валилось с ошибкой парсинга аргументов при старте.
2. Даже если бы флаг существовал: демон создавал kernel TUN-интерфейс
   (`ip tuntap add ...`) и сразу переключал на него `default route`, но
   **ничего не перекачивало пакеты** между этим TUN и ядром. На Desktop-версии
   (Windows/Wintun, отчасти Linux) этим занимается отдельный кусок Go-кода
   (`Desktop/*/Libs/bridge.go` + платформенный `Start(udpConn, ...)`), а для
   OpenWRT такой код никогда не был написан — в `go.mod` даже осталась
   неиспользуемая зависимость `github.com/songgao/water` (Go-библиотека для
   TUN/TAP), явно оставленная "на будущее".
3. Не прокладывал обходные маршруты к самому VPN-серверу — включив
   default route через ещё не поднятый туннель, роутер потерял бы связь с
   сервером, через который этот туннель поднимается.
4. Не трогал firewall — даже с рабочим туннелем клиенты в LAN не получили бы
   выход в интернет (нет masquerade/forwarding на новый интерфейс).

Код в этом каталоге чинит все четыре пункта. Собранный демон
(`GOOS=linux GOARCH=arm64 CGO_ENABLED=0`) я проверил — собирается чисто,
статически слинкован, весит ~5.9 МБ.

## Компоненты и совместимость с Cudy TR3000

Cudy TR3000 — MediaTek MT7981 (Filogic 820), 2×Cortex-A53, **arm64**,
таргет OpenWrt `mediatek/filogic`. 256 МБ — это встроенная flash-память
(eMMC/NAND), а не оперативная — ОЗУ на этой модели 512 МБ, так что запас по
памяти для демона (~6 МБ) и клиента (~15–25 МБ) вполне комфортный. Компилировать
что-либо прямо на роутере не нужно — обе части кросс-компилируются на
обычном ПК/CI и просто копируются как готовые бинарники.

Современный OpenWrt (24.10 и новее, в том числе то, что вы называете
"OpenWrt 25") по умолчанию использует **firewall4 (nftables)** — код здесь
рассчитан именно на него (использует `list device` в зоне firewall,
специфичную для fw4 фичу).

## ⚠️ Единственное, что осталось нерешённым: glibc vs musl

`csqtt-core` (`Endlad2/csqtt-core`) собирает готовые релизы клиента под
`aarch64-unknown-linux-gnu` — это **glibc**. Стоковый OpenWrt использует
**musl**. Собранный под glibc бинарник на musl-роутере не запустится.

Я не стал сходу кросс-компилировать `csqtt-client` под
`aarch64-unknown-linux-musl` в этой сессии: в его `Cargo.toml` есть
`aws-lc-rs` (собирает C-код AWS-LC) и запатченный `primp`
(`vendor/primp`, обёртка над импersonation-HTTP-клиентом с нативной TLS-
библиотекой) — такие зависимости кросс-компилируются под musl не всегда
гладко и без тестового железа под рукой я не хочу выдавать вам бинарник,
который я не могу проверить. Три пути решить это:

1. **Я соберу его сейчас через `cargo zigbuild`** (Zig умеет линковать под
   musl без отдельного тулчейна) — скажите, и я попробую в фоне; если
   соберётся, пришлю готовый `csqtt-client-arm64-musl`.
2. Собрать самим на любой Linux-машине: `rustup target add
   aarch64-unknown-linux-musl`, дальше см. `OpenWRT/README` в самом
   `csqtt-core` репозитории или CI (`.github/workflows/build.yml`) как
   образец кросс-сборки под glibc arm64 — тот же процесс, только target
   `-musl`.
3. Поставить на роутер [Entware](https://github.com/Entware/Entware) — там
   есть свой glibc-совместимый рантайм (`/opt`), и релизный
   `client-linux-arm64` из `csqtt-core` можно попробовать запустить через
   него как есть. Не проверял, но это стандартный обходной путь для glibc-
   бинарников на OpenWrt.

Без рабочего `csqtt-client` под вашу архитектуру демон честно запустится,
но `Connect()` будет падать сразу же на попытке `exec` — в логах
(`/api/logs` или `logread`) это будет видно однозначно.

## Установка

### Вариант «одной командой»

С машины, которая находится в одной сети с роутером:

```sh
./install.sh root@192.168.1.1 ./csqtt-daemon-arm64 ./csqtt-client-arm64
```

Третий аргумент необязателен — можно поставить сначала только демон, а ядро
положить в `/usr/bin/csqtt-client` позже. Скрипт проверит архитектуру и
наличие `fw4`, скопирует файлы, включит сервис и покажет статус; уже
существующий `/etc/csqtt/csqtt.conf` он не перезатирает.

Дальше — вручную, по шагам:

### 1. Соберите демон (или возьмите готовый бинарник)

```sh
cd OpenWRT
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-s -w" -o csqtt-daemon-arm64 .
```

### 2. Скопируйте на роутер

```sh
scp csqtt-daemon-arm64 root@192.168.1.1:/usr/sbin/csqtt-daemon
scp files/csqtt.init      root@192.168.1.1:/etc/init.d/csqtt
scp files/csqtt.conf.example root@192.168.1.1:/etc/csqtt/csqtt.conf
scp /path/to/csqtt-client-arm64  root@192.168.1.1:/usr/bin/csqtt-client   # см. раздел про glibc/musl выше
```

### 3. На роутере

```sh
chmod +x /usr/sbin/csqtt-daemon /usr/bin/csqtt-client /etc/init.d/csqtt
vi /etc/csqtt/csqtt.conf   # заполнить PEER, PASSWORD, VK — см. ниже
/etc/init.d/csqtt enable
/etc/init.d/csqtt start
```

### 4. Проверка

```sh
curl -s http://127.0.0.1:8080/api/status
curl -s http://127.0.0.1:8080/api/logs | tail -n 40
curl -s -X POST http://127.0.0.1:8080/api/connect
```

Если через 5–10 секунд в логах видно `[TUN] Туннель поднят: csqtt0 ...` —
значит TUNCONF получен, трафик пошёл, default route и firewall настроены.
Проверьте с любого устройства в LAN: `curl ifconfig.me` должен вернуть IP
сервера, а не ваш реальный.

Отключение: `curl -s -X POST http://127.0.0.1:8080/api/disconnect`.

## Откуда взять PEER/PASSWORD/VK

Из вашей ссылки вида:

```
csqtt://connect?v=2&host=HOST&peer=PORT&password=PASSWORD&hashes=HASH1+HASH2+HASH3
```

- `PEER` в конфиге = `HOST:PORT` (склеить `host` и `peer` из ссылки через
  двоеточие).
- `PASSWORD` = `password` из ссылки как есть.
- `VK` = `hashes` из ссылки, `+` замените на запятые (или оставьте пробелы —
  демон сам нормализует любые разделители).

## Ограничения этой реализации

- **Один конфиг**, без мультипрофильного UI из `Frontend/app.html` (тот
  ожидает полноценный REST — `/api/configs`, `/api/settings` — которого нет
  ни в оригинальном демоне LaLune, ни здесь). Настройка — через
  `/etc/csqtt/csqtt.conf` или `POST /api/config/update`.
- Только IPv4 (как и весь остальной проект на данный момент).
- DNS туннеля дописывается в `/etc/resolv.conf` напрямую; на части конфигов
  OpenWrt это симлинк, управляемый dnsmasq/netifd, и может быть перезаписан
  при следующем сетевом событии — если DNS будет "слетать", подскажите,
  сделаю через `uci` (`/etc/config/dhcp`) вместо прямой записи в файл.
- Обходные маршруты строятся по IP из `PEER`/`TURN_HOST` и по IP, которые
  ядро упоминает в логах со словом `TURN`/`Relay` во время работы — если
  сервер меняет relay на лету, соответствующий маршрут добавится
  автоматически, но с небольшой задержкой (до ~0.4 c, интервал опроса лога).
